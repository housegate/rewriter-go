## OVERVIEW

`rewriter-go` is a native Go implementation of the ClickHouse SQL `Rewriter` interface, backed by the `tobilg/polyglot` Rust engine through PureGo FFI. It is library-first: root package APIs and the stateless `Service` are the product surface; the implementation routes SELECT, write/DDL, DB-level, EXISTS/SHOW CREATE, and GRANT/REVOKE statements through internal handlers.

## CONVENTIONS

- Protobuf source and generated Go types are owned by `github.com/housegate/rewriter-proto`; this repo imports its `gen/pb` package and does not generate protobuf code locally.
- `third_party/polyglot-src` is a git submodule, not first-party code. Do not refactor upstream internals from this repo.
- `go.mod` uses `replace github.com/tobilg/polyglot/packages/go => ./third_party/polyglot-src/packages/go`; submodules are required even for pure-Go builds.
- `go.mod` currently declares `go 1.25.0`; GitHub workflows currently install Go `1.22`. Verify the intended toolchain before changing either side.
- There is no repo-local formatter/linter config. Use `gofmt`; CI enforces `go vet ./...`.
- `POLYGLOT_SQL_FFI_PATH` gates engine-backed tests. Plain `go test ./...` runs pure-Go tests and skips FFI-dependent tests.
- `REWRITER_ORACLE_ADDR` enables optional differential checks against a live `rewriter-grpc` oracle; default local tests do not require it.
- Package tests keep fixtures in package-local `testdata/`. Harness corpora are JSON; engine AST characterization snapshots live under `internal/engine/testdata/ast-shapes` and are regenerated by `internal/engine/characterize_test.go`.
- Storage-integrity (Spec G) goldens live in `internal/harness/testdata/storage_integrity_cases.json`; the C++ repo carries a byte-identical copy. The frozen schema, exact-SQL rules, paired-copy procedure, and `UPDATE_GOLDEN` commands live in `internal/harness/AGENTS.md` under **STORAGE-INTEGRITY CORPUS CONTRACT**.
- Storage-integrity lookup precedence selects a physical surface but does not authorize it: logical SI databases (including INSERT targets) must be present in `database_map`. Every database containing a configured safe/unsafe table is protocol-owned; table nodes/functions, current-db context, DB-level DDL/DCL, and USE/SHOW must reject direct access with SI-classified metadata.
- Prefer semantic SQL equality through polyglot AST diff where output formatting can differ from ClickHouse formatting. The storage-integrity corpus is the deliberate exception: every successful case is pinned exactly after its shared literal-aware identifier-quote normalization, with per-engine pins for declared divergences.
- `NativeRewriter` is per-connection and stashes the last successful rewrite for error inversion. `Service` is stateless and re-derives forward maps from the request for `RewriteErrorMessage`.
- `doRewrite` owns dispatch order and reject normalization: writes, DB-level, DESCRIBE, EXISTS/SHOW CREATE, GRANT/REVOKE, SELECT, then pass-through.

## Table-reference policy (spec 2026-09-26)

The policy checks apply only to requests that select `nameresolve.ModeDynamic`. The IN-operand decoder below is shared by every mode, so a static-mode IN operand at any paren depth, or a bare quoted `` `db2.x` ``, is rewritten like a static-mode FROM table (`a IN ((x))` → `a IN ("p.x3")` for a table_map entry `x → p.x3`).

Where it lives:

- `internal/handlers/preflight.go` — `PreflightTableReferences` (the ordered checks below), `commandClassModelled`, `rejectDisallowedCarriers` (T5), `rejectUngovernedReads` (R2 / R5), `CheckSessionSet` (the SET carve-out).
- `internal/engine/parameters.go` — T2 (`TablePositionParameter`, `IdentifierParameterInText`).
- `internal/engine/nodes.go` — the ordered walker (`walkStatementObjects`) and the one IN-operand decoder, `decodeInOperand`, used by every IN consumer.
- `internal/engine/references.go` — T3 database collection (`CollectDatabaseReferences`, `CollectDatabaseReferenceSets` — every database plus the SI-handler-blind subset, which is the string-lookup arguments) and the T6 string-lookup family.
- `internal/engine/create_empty.go` — `StripCreateTableEmpty` / `InsertCreateTableEmpty`: `doRewrite` rewrites `CREATE TABLE … EMPTY AS SELECT` without its `EMPTY` keyword (Polyglot drops the body otherwise) and puts it back; if the statement was rewritten but `EMPTY` cannot be reinserted (or the tokenizer fails on a body-less `create_table`), dynamic mode refuses (seals) it as `UnsupportedStatement` via `sealCreateTableEmpty`, while static and no-rewrite requests keep the Go-error channel; if no `EMPTY`-stripped candidate reparses into a `CREATE TABLE … AS SELECT` (for example a clone form such as `CREATE TABLE db1.n AS db1.src ENGINE = Memory EMPTY AS SELECT …`), no `EMPTY` is found and the whole-statement parse gate refuses the original statement, which Polyglot cannot consume in full because of the `EMPTY` keyword; a statement whose stripped candidate does reparse but whose text Polyglot truncates (`… EMPTY AS SELECT … XYZ`) has its `EMPTY` found and stripped, the gate refuses the stripped text, and `doRewrite` echoes the caller's original SQL like every other non-`Success` response. The annotation fallback in `AnnotateStorageIntegrityRejectAST` changes only the message of a rejection, never its code.
- `internal/engine/ungoverned.go` — `walkGenericExpression` (column / constraint / storage-property / ALTER-action expressions), `ExpressionPositionHasReads`, and the opaque text scans (`OpaqueStatementTexts` = `OpaqueAlterTexts` + `ViewColumnListRawTexts`, `OpaqueTextDatabases`, `OpaqueTextIsUngoverned`).
- A view's column list is governed like a CREATE TABLE one. Polyglot keeps a view's typed column list under `create_view.schema` (a CREATE TABLE's under `columns` / `constraints`), which the walker and `ExpressionPositionHasReads` walk as column expressions; it keeps an INDEX / PROJECTION / PRIMARY KEY item as an opaque `raw` node, whose text for an INDEX over anything but a bare column is the Rust debug form of the parsed expression. `ViewColumnListRawTexts` therefore returns the *source* text of each raw item, located in the SQL's token stream (the first depth-0 parenthesis group of the header, split at depth-1 commas and paired one to one with the parsed items; any mismatch fails closed), and every opaque-text scan below reads it like Raw ALTER text. A `PROJECTION name (SELECT …)` item gets the ADD PROJECTION body rule.
- `internal/engine/settings.go` — SQL-bearing and dialect settings and the setting-value rule.
- `internal/engine/allowlists.go` — T5 classification and messages.
- `internal/engine/wholestmt.go` — `CheckParsedInFull`, the whole-statement parse gate (see below).
- `internal/engine/regenerated.go` — `CheckRegenerated`, the mid-statement drop gate (see below); its literal / number decoding is in `regenerated_lexeme.go` and its precedence scans in `regenerated_precedence.go`.
- `native.go` — dispatch order, the whole-statement parse gate, the mid-statement drop gate in `finalize`, the final unmodelled-class refusal and the SET carve-out, and `sealStorageIntegrityHandlerError`.

Message families (six; exact texts are cross-engine contract):

- T2 `engine.IdentifierParameterMessage` — `query parameters are not supported in a database or table position` (InvalidRewriteRequest).
- T3 `nameresolve.ProtectedDatabaseRejectMessage(db)` — `protected database <db> is not addressable` (InvalidRewriteRequest).
- T5 `engine.TableFunctionRefusedMessage` / `TableFunctionUnknownMessage` / `TableEngineRefusedMessage` / `TableEngineUnknownMessage` / `TableSettingRefusedMessage` — `table function|engine <name> is not accepted|recognised`, `table setting <name> is not accepted` (UnsupportedStatement).
- T6 `stringLookupUnresolvedMessage` — `<fn> target "<arg>" does not resolve through the caller's databases` (InvalidRewriteRequest in the preflight; UnsupportedStatement inside an embedded INSERT … SELECT / CTAS body). A non-literal first argument reports `target ""` on every path.
- Unresolved unqualified name `nameresolve.UnresolvedUnqualifiedTableMessage(t)` — `unqualified table "<t>" does not resolve through the session's logical database` (InvalidRewriteRequest; UnsupportedStatement inside an embedded INSERT … SELECT / CTAS body): in dynamic mode, a read-position table with no database qualifier — including the one-part dotted quoted form `` `db1.t` ``, whose table is `db1.t` — whose logical context is empty, unmapped or maps to a missing remote upstream. ClickHouse would resolve the verbatim name in the session's current database, which housegate makes the physical database, so the SELECT walker refuses it instead of skipping it. The table name is inserted verbatim, without escaping a `"` it contains, like T6. When it is the final answer, the rejection carries an empty `table_rewrites` in every statement family, including the enclosing write statement's own targets; a refusal that outranks it (the SI write refusal of a view / MV body) keeps the map it would have without the unresolved name. CTE names never reach the walker's table callback, and a qualified unmapped name (`db2.x`) stays a lenient skip. DESCRIBE / EXISTS / SHOW CREATE / SHOW COLUMNS and write targets already refused these names with their own messages and are unchanged. Its precedence is under step 8 below.
- T7 `engine.UnsupportedStatementMessage` — `statement is not supported` (UnsupportedStatement): a statement the engine did not parse in full or regenerates as a different statement (in every mode and both SI states), a command clause a handler cannot re-render, an unmodelled statement class, a read in a position no rewrite reaches, a non-plain setting value, a Go error. With the SI surface active the unmodelled-class refusal is `nameresolve.StorageIntegrityUnmodelledMessage` instead, and an SI object the statement names upgrades it to the SI message for that object.

IN operands: `decodeInOperand` unwraps parentheses and operand aliases to any depth and in any interleaving (`a IN (db.t AS z)` and `a IN ((db.t) AS z)` are `a IN db.t`: ClickHouse reads `db.t` for them, and the rewrite drops the alias, which ClickHouse lets nothing else reference), treats a parameter operand as T2, and decodes an identifier structurally — a bare quoted `` `db2.x` `` is an unqualified table named `db2.x` in the session's logical database (`phys."db1.db2.x"`), exactly like FROM. A literal list is a value list. A bare keyword operand (`a IN NOW`, `a IN (current_user)`), which Polyglot parses as a no-parens function call, is an unqualified table like `a IN b` (`noParensKeywordName`): ClickHouse 26.2 reads the table of that name in the current database under both analyzers.

Known deviation from ClickHouse: a bare identifier operand (`a IN b`, `a IN (b)`, and equally an aliased one, `a IN (b AS z)`, whose alias the rewrite drops) is rewritten as the table `b` in the session's logical database; an alias-qualified `a IN (tt.b AS z)` is reported as the logical table `tt.b` and forwarded unchanged. ClickHouse 26.8 resolves `b` there as a column first and only then as a table. The rewriter has no schema to decide which, and forwarding the operand unrewritten would let ClickHouse bind a table of that name in the physical database; rewriting fails safe (it can only reach the tenant's own governed table), at the cost of refusing (with an unknown-table error from ClickHouse) a legitimate `a IN (b)` that meant a column. Use `a IN tuple(b)` or `a = b` for the column form.

No WITH binding in an R2 position: a structured UPDATE / DELETE, INSERT VALUES rows, and every column, constraint (CHECK / ASSUME, in CREATE and ALTER ADD CONSTRAINT), INDEX, TTL or other non-engine storage expression of CREATE TABLE / CREATE VIEW / ALTER is walked in an unbound scope (`engine.unboundScope`). ClickHouse qualifies every table name there with the current database before a WITH clause is consulted, so `DELETE … WHERE a IN (WITH x AS (…) SELECT a FROM x)` and a CHECK constraint over the same subquery read the physical table `x`, and a stored constraint reads `FROM phys.x` (measured on 26.2 and 25.8 under both analyzers, including `WITH RECURSIVE` and a CTE one subquery deeper; a WITH expression alias and a projection alias do not bind there either, except that a lightweight UPDATE and a table `TTL … WHERE` written in CREATE TABLE bind them, which the engine refuses anyway, while `ALTER … MODIFY TTL … WHERE` reads the table; a table-source alias reads the table under both analyzers; on 25.8 an `ORDER BY` / `PRIMARY KEY` / `SAMPLE BY` / `PARTITION BY` key, a column TTL and a CREATE-time TTL read the table in the `default` database). In an unbound scope neither a CTE nor an alias binds, so the name is a table like any other and R2 refuses the statement exactly as it would with an unrelated CTE name. A CTE keeps binding in a SELECT, an INSERT … SELECT / CTAS body and a view / MV body, both from the statement's own WITH and from a subquery.

Names that bind an unqualified IN operand (`readSourceScope` in `internal/engine/nodes.go`), measured on ClickHouse 26.2 with `enable_analyzer=1` and `=0` (a tenant picks the analyzer per query or per session): a read-query CTE name, and a WITH expression alias whose value is provably not a table reference (a literal, a tuple or array of literals, a parenthesised function call, a scalar subquery, or operators over literals: `withValueIsNotTableReference`; a no-parens keyword such as `NOW` or `CURRENT_DATE`, which Polyglot parses as a function call, is an identifier to ClickHouse), bind it in every nested scope, even under a same-named table alias; a projection alias binds it only in its own SELECT. A WITH alias whose value is an identifier — bare, quoted, parenthesised, qualified, unresolvable, or another alias, so every chain — binds nothing and shadows an enclosing binding of its name: ClickHouse reads a table through it (`WITH nosuch AS "other.secret" … a IN "other.secret"` reads `phys."other.secret"` and `WITH "db1.t" AS z … a IN z` the ordinary physical table of Active `db1.t` under the new analyzer; nested, the new analyzer reads the table named after the alias and the old one substitutes the identifier and reads it). Any other operand name is a table in the session's logical database, rewritten, reported and SI-checked like `a IN b`. A table-source alias (FROM / JOIN table, subquery, table function) never binds it: ClickHouse reads the table of that name in the current database for an enclosing SELECT's alias under both analyzers, and for the IN's own SELECT's alias under `enable_analyzer=0`. The current database is the physical one, so forwarding the operand read another tenant's table (`FROM db1.o AS "other.secret" WHERE a IN (SELECT … WHERE a IN "other.secret")`) or the ordinary physical table of an Active SI table, unreported. An enclosing SELECT's projection alias does not bind it either (the old analyzer reads the table). Cost: under the default analyzer, a same-scope `a IN o1` with `o1` a table alias, or a nested `a IN z` with `z` an outer projection alias, now reads the table `o1` / `z` (usually an unknown-table error) instead of the alias; write the subquery or the expression out instead.

## Whole-statement parse gate

The pinned Polyglot's ClickHouse dialect accepts statements it has not consumed: `Parser::parse` skips every token after the point where its grammar stops ("ClickHouse fallback: consume unconsumed tokens until semicolon/EOF"), discards a statement-level `SETTINGS` / `FORMAT` tail the statement's own grammar does not model, and closes any bracket the input left open at end of input. Generating from that AST produces SQL that means something other than the input: `CREATE TABLE db1.n ENGINE = Memory XYZ AS SELECT * FROM phys.x` became `CREATE TABLE db1.n ENGINE=Memory`, and `… JOIN other.u WITH OFFSET AS off ON 1` lost its `ON` clause.

`engine.CheckParsedInFull(e, sql, ast)` measures consumption, because Polyglot reports no position: every `(` `[` `{` token must be closed by its own kind, and cutting `sql` before its last token that is neither a bracket, a semicolon nor a zero-width token must change the AST (a byte-identical AST means the parser stopped at or before that token, or discarded it). Zero-width tokens are never a cut point: the tokenizer emits one at end of input for the text after `INSERT … FORMAT <name>`, so a trailing comment there does not fail the gate. An `INSERT … FORMAT <name>` payload is data and is not checked. A tokenizer failure fails closed. The binary search that names the stop point in the error text never decides the outcome.

Every entry point that turns user SQL into generated SQL runs it right after `ParseOne`: `rewriteStatement` (T7 refusal, precedence step 0, after the live-view classifier and before `PreflightTableReferences`), `doMaterializeSQL` (`MaterializeSyntaxError` with the detailed message) and `AnalyzeSnapshot` (the `INVALID_INPUT` statement refusal). `StripCreateTableEmpty` parses the original `EMPTY` statement without the gate: the gate runs on the `EMPTY`-stripped text that is actually rewritten.

Polyglot also cannot fully parse some statements that are valid ClickHouse, for example statement-level `SETTINGS` on `DROP` / `CREATE DATABASE` / `DELETE` / `UPDATE`, `CREATE DATABASE … ENGINE`, `DROP … NO DELAY`, `LIMIT … WITH TIES` when it ends the statement, `INTO OUTFILE`, `CREATE [OR REPLACE] VIEW … AS (SELECT …) COMMENT '…'` and its `CREATE MATERIALIZED VIEW … AS (SELECT …) COMMENT '…'` form, `CREATE DATABASE … COMMENT '…'`, `… OFFSET n ROWS FETCH FIRST|NEXT m ROWS ONLY` and `INSERT … FROM INFILE` (which the no-rewrite mode used to answer `Success` for a different statement, `INSERT … SELECT * FROM INFILE`; dynamic requests already refused it). That is an engine-internal limit: the gate refuses them as T7 before T2 / T3. Such shapes are engine-local, stay out of the shared corpus, and the C++ engine is not required to match their code or message.

Known residual of this gate: a clause Polyglot consumes but drops or prints differently is not a consumption failure and passes it. The mid-statement drop gate below refuses those.

## Mid-statement drop gate

The pinned Polyglot consumes every token of some statements but parses a clause into nothing or prints it differently, so the SQL generated from the AST means something else while the whole-statement parse gate passes it. Measured on the parse-gate head (Polyglot v0.12.1 and v0.13.0 behave identically): `DELETE … IN PARTITION` dropped (widening a destructive statement to every partition), `DROP TABLE` / `VIEW` / `DATABASE … ON CLUSTER` dropped, `DROP TEMPORARY TABLE n` regenerated as `DROP TABLE n`, `DROP TABLE IF EMPTY` regenerated as `DROP TABLE`, `LIMIT … WITH TIES` dropped before `FORMAT` / `SETTINGS` and in subqueries, `LIMIT n BY … LIMIT m` regenerated as `LIMIT m BY …`, a column's `EPHEMERAL` / `STATISTICS` / `SETTINGS` dropped, `INSERT INTO t (* EXCEPT …)` / `(COLUMNS(…))` column lists dropped, `TRUNCATE … SETTINGS` dropped, `::T` and `CAST(x AS <SQL alias>)` wrapped in `Nullable`, and function respellings that are not ClickHouse aliases (`CHAR_LENGTH` → `LENGTH`, `instr` → `POSITION`, `toStartOfDay(x)` → `dateTrunc('DAY', x)`, `group_concat(s, sep)` → `GROUP_CONCAT(CONCAT(s, sep))`, `startsWith` → `STARTS_WITH`, `toTypeName` → `TYPEOF`). Polyglot also keeps a streamed-VALUES INSERT with no rows (`INSERT INTO db1.o (a, b) VALUES`, `INSERT INTO db1.o SETTINGS … VALUES`, the shape a 25.x `clickhouse-client` sends) as a `command` node whose text is `INSERT INTO VALUES`, table and columns gone; before the gate compared command text, none and static mode answered `Success` with that text.

`engine.CheckRegenerated(e, sql, ast)` tokenizes the input and Polyglot's identity `Generate(ast)` with the engine's raw tokenizer and compares them as multisets of spellings: commas, parentheses, dots and semicolons dropped, words upper-cased, the ClickHouse aliases in `spellingClass` folded, strings and numbers distinct. The multiset cannot see order, so the column-declaration modifiers `DEFAULT` / `MATERIALIZED` / `ALIAS` / `EPHEMERAL`, `COMMENT`, `CODEC`, `TTL` and `PRIMARY KEY` are also compared in order, per column declaration (`columnModifierOrder`, reading only the column list of `CREATE TABLE` / `VIEW` / `DICTIONARY` and each `ALTER … ADD` / `MODIFY COLUMN`, so a table-level `COMMENT` / `TTL` that Polyglot prints after a CTAS `SELECT`, a column named like a modifier outside a declaration, and an `INDEX` Polyglot moves after the columns do not count): ClickHouse accepts them in that order only, and Polyglot prints a column's modifiers in an order of its own, which turns a rejected `CODEC(ZSTD) COMMENT 'x'` or `TTL … DEFAULT 1` into an accepted `COMMENT 'x' CODEC(ZSTD)` / `DEFAULT 1 TTL …`, and an accepted `MATERIALIZED 1 COMMENT 'x'` into a rejected one; any change in that order refuses. A `NodeKind` error, a tokenizer error and a generator error are returned as is, so every non-nil result means the statement is not known to be regenerated faithfully. A `command` or `raw` node is compared by its own text (`CommandSQL` / `RawSQL`, which is what `Generate` prints for it) under the same rules, with one addition: there a quoted identifier is spelled apart from the same word bare. That text is usually the input, but not always: the streamed-VALUES `INSERT INTO VALUES` above, and a raw node, which Polyglot prints from its tokens with every quoted identifier's quotes dropped, a `DEFINER` / `SQL SECURITY` prefix of `CREATE … LIVE VIEW` lost and a `$tag$` heredoc mangled. Dropped quotes can name another statement (``CREATE ROW POLICY … USING `null` = 1`` printed as `USING null = 1` filters on the `NULL` literal, measured on 26.2; `` `true` ``, `` `false` ``, `` `inf` `` and `` `nan` `` lose their quotes the same way), so a raw node with any quoted identifier refuses; a command node keeps its quotes (`` GRANT … TO `null` `` passes), and structured nodes are regenerated with their quotes. The code lives in three files: `regenerated.go` (entry point, spelling table, INSERT tail rules), `regenerated_lexeme.go` (literal and number decoding) and `regenerated_precedence.go` (isolated-operator and ternary scans). A closed table of measured cosmetic respellings of the input is applied: `NULLS LAST` (ClickHouse's default in both directions), `SELECT ALL`, `TOP n`, `LIMIT n, m`, `DIV` / `MOD`, `REGEXP`, `<=>`, `NOT LIKE` / `NOT ILIKE`, `a ? b : c`, `POSITION(x IN y)`, `INTERVAL n`, heredoc bodies, `DEFINER = 'u'`, `VARCHAR(n)`, the optional `TABLE` keyword, and the aliases in `spellingClass`. An added `AS`, `=` or comma join's `CROSS JOIN` is neutral; any other lost or added spelling fails.

Literals and quoted identifiers are compared on their raw source lexemes decoded with ClickHouse's escape rules (`clickhouseUnquote`, measured on 26.2 and 26.7.5.10), never on the text Polyglot decoded: Polyglot reads `\_`, `\%`, `\N`, `\Z` and `\/` differently, so `LIKE 'x\_%'` regenerates as `LIKE 'x_%'` and ``db1.`a\_b` `` as `db1."a_b"`, which name another pattern and another table. `'…'` is a string and `"…"` / `` `…` `` are identifiers, all decoded alike; the Unicode quotes `‘…’` / `“…”` and heredocs keep their body verbatim; `x'…'` and `b'…'` compare by the bytes they spell. A lexeme ClickHouse would read with a different extent (a trailing backslash, a lone quote, a `\x` that reaches the closing quote) is undecodable and refuses. Numbers are compared by value and ClickHouse type (`numberKey`): a decimal, `0x` or `0b` integer up to 2^64-1 is one unsigned integer (`0x1F` equals `31`), every other literal is a Float64 keyed by its exact rational value (`1e3` differs from `1000`, `.5` equals `0.50`). A `_` is accepted only when it sits between two digits of the literal's radix (`1_000`, `0x1_F`); `1e_3`, `0x_1F`, `1_e3` and `0x1F_` are identifiers in ClickHouse, and a number directly followed by a letter or `_` is refused.

Some respellings change an operator's precedence class, so the regeneration can regroup the operands: `a <=> b` prints as `a IS NOT DISTINCT FROM b`, `NOT a DIV b` as `intDiv(NOT a, b)`, `a NOT LIKE b = c` as `NOT a LIKE b = c`, each of which ClickHouse reads differently. Such a respelling is cosmetic only for isolated operands (`isolated`): both operands are a single token, a dotted name or a `{p:T}` parameter, and the application is bordered on both sides by a clause keyword, a comma, a bracket, `AND` or `OR`. An `AND` border counts only when `isLogicalAnd` proves it is not the `AND` of a `BETWEEN`: the scan runs back over the left operand chain, takes each balanced bracket pair and each balanced `CASE … END` as one unit, pairs every `BETWEEN` with the next `AND`, and refuses anything it cannot classify. Only the `AND` that a `[NOT] BETWEEN` owns fails to border, including one whose lower bound is a `CASE … END` (`x BETWEEN CASE … END AND a <=> b`, and the `NOT LIKE` / `REGEXP` forms, are refused); a `NOT BETWEEN`, `NOT LIKE` or `REGEXP` earlier in the chain before a logical `AND` passes (`x NOT BETWEEN 1 AND 2 AND a REGEXP 'q'`). Anywhere else the input keeps its own spelling, which the regeneration does not contain, and the statement is refused. Operators Polyglot keeps verbatim (the expressions of `ALTER … DELETE` / `UPDATE`) are exempt: `operatorsKept` finds them in the regeneration and their input spelling then matches as is. The ternary `a ? b : c` is `IF(a, b, c)` only when the whole ternary is bordered and made of measured operators (`ternaryColon`); an `OR` in the else branch is refused, because ClickHouse rejects `a ? b : c OR d` while `IF(a, b, c OR d)` would make it valid.

INSERT payloads are compared only where they are not data. An INSERT whose AST carries a `FORMAT` data clause (`insertHasFormatClause`; a column or alias named `format` is not one) is compared up to the name after its last `FORMAT`. For `INSERT … SELECT … FORMAT <name> <text>` without `input()`, `<text>` is dropped from the comparison only when it is whitespace and comments (`withoutIgnoredData`, which ClickHouse ignores); any other text is compared, so its loss refuses. A statement that reads `input()` anywhere (`readsInput`: `input` followed by `(` in any case, in a CTE or subquery too) is checked on its token stream whatever its shape (plain SELECT, `UNION` / `INTERSECT` / `EXCEPT`, a CTE before either): when it ends in `FORMAT <name>` after a SELECT, only `[ \t]*\n?` may follow the name (`isStreamedDataTail`), because ClickHouse reads everything else, blank lines and comments included, as rows; a `FORMAT` token anywhere else refuses; without one the statement has no data position and is compared in full.

The command handlers that re-render a statement from parsed fields hold the same rule at the point they would answer `Success`, since `CheckRegenerated` compares a `command` node's own text, not the SQL a handler renders from it. EXISTS / SHOW CREATE / DESCRIBE (`ObjectTarget`) refuse any token after the name (`Trailing`) and a `TEMPORARY` table that would be qualified into an ordinary one; a missing or unrecognised target (no target, or a keyword-lexed first token such as `system` / `default`) is refused in every mode, not only under dynamic args; a `SHOW CREATE` whose object word is an access-entity word (`USER[S]`, `ROLE[S]`, `QUOTA[S]`, `PROFILE[S]`, `POLIC{Y|IES}`, and the `ROW`, `SETTINGS` and `MASKING` prefixes of `ROW POLICY` / `SETTINGS PROFILE` / `MASKING POLICY`; an unquoted word only) with no `TABLE` / `DATABASE` / `VIEW` / `DICTIONARY` before it is refused in every mode and never rendered as `SHOW CREATE TABLE <word>`. `USE` refuses trailing tokens when it would rewrite to a physical database. `SHOW TABLES` models only `[{FROM|IN} <db>]`, so `LIKE`, `LIMIT`, `FORMAT`, `SETTINGS` and the `EXTENDED` / `FULL` / `TEMPORARY` variants are refused. `SHOW DATABASES` models only an optional `LIKE` over a single-quoted pattern: the pattern's raw lexeme (`DBLevelInfo.LikeRaw`) is carried verbatim, because re-escaping the decoded text turns a literal `\_` into a wildcard; a pattern that is not single-quoted, trailing tokens, the `EXTENDED` / `FULL` / `TEMPORARY` prefixes and `FROM` / `IN` (which ClickHouse rejects, and the rewrite must not make valid) are refused. A refusal an earlier step owns keeps its own code and message (`TestCommandPrefixKeepsPolicyRefusal`).

`doMaterializeSQL` runs `CheckRegenerated` on the AST of the caller's SQL, before `MaterializeNonDeterminism` substitutes `now()` / `rand()` / UUID literals, and only when there is at least one replacement, because it then regenerates the statement with the same generator: a statement the generator would change is answered `MaterializeUnsupportedStatement` with the SQL unchanged and no replacements, so the agent never signs a statement the client did not write. The materialize plugin falls open to the original SQL. `AnalyzeSnapshot` is not gated by the drop check: it runs only `CheckParsedInFull` and reads a closed typed scope graph, which refuses most measured shapes (`WITH TIES`, `LIMIT … BY`, `::`, `<=>`, `DIV`, `LIKE`, `NULLS LAST` and the function respellings) but not the `INSERT` column lists Polyglot drops. It currently accepts `INSERT INTO t (* EXCEPT (b)) SELECT …`, `INSERT INTO t (COLUMNS('v')) SELECT …` and `INSERT INTO t (*) SELECT …`, plans each as `INSERT INTO t SELECT …` and reads it as all target columns (`snapshot_query.go` treats an absent column list that way), so it binds a different column set than the client wrote. Known gap: fix it (gate `AnalyzeSnapshot` with `CheckRegenerated`, or refuse those column lists) before the signed `INSERT … SELECT` lane (issue #153, default-off and not wired) is wired.

Unquoted-alias injection class: Polyglot drops the quotes of a quoted alias on a bare parenthesised tuple (`WITH (1, 2) AS "x SELECT a FROM phys.`other.secret` --" …`, and the same in a projection or any expression position), so the alias text runs as SQL and reads another tenant's table; array literals, `tuple(…)`, `map(…)` and scalar subqueries keep their quotes. `CheckRegenerated` is the only barrier, and `TestMidStatementDropGateUnquotedAlias` pins it in every mode. The gate also refuses (`checkBareTokens`) any regenerated unquoted token that contains a `#`: Polyglot's tokenizer keeps `x#` as one word, so the spelling comparison cannot see that `AS "x#"` became `AS x#`, and ClickHouse (measured on 25.8 and 26.8) reads `# ` as a comment to the end of the line, silently dropping the rest of the statement, and any other `#` in a word (`x#x`) as an unrecognised token. Other characters a generator can unquote (`@`, `$` first, non-ASCII, digits-first) make ClickHouse fail with a syntax error instead of changing the statement; the gate does not refuse them for that reason. A `#` in a string, a quoted identifier or a real comment is not a token character and is untouched.

Extend the tables only with ClickHouse evidence (an `alias_to` entry or an execution comparison) and a `TestCheckRegenerated` row.

Refused although cosmetic (fail closed, measured): unary `+`, `INSERT INTO t (*) VALUES`, `locate(a, b)` and a `DOUBLE PRECISION` column type. Not detected, none of which changes what a statement ClickHouse accepts does: reorderings outside the column-modifier list, `DESC COLLATE 'en'` regenerated as `COLLATE 'en' DESC` and `FROM t FINAL SAMPLE 0.5` as `SAMPLE 0.5 FINAL`, both of which ClickHouse 26.2 rejects in the new order; a column's `NULL` / `NOT NULL` moved before its other modifiers, which is not in the ordered list because Polyglot also moves it where ClickHouse accepts both orders (`MATERIALIZED 1 NULL` → `NULL MATERIALIZED 1`), so `CODEC(ZSTD) NOT NULL` and `TTL … NULL`, which ClickHouse rejects, regenerate as `NOT NULL CODEC(ZSTD)` / `NULL TTL …`, which it accepts; the neutral `AS` taking an interval unit as an alias, `INTERVAL '2' * 1 DAY` → `INTERVAL '2' * 1 AS DAY`, which ClickHouse rejects, so an added `AS` is not proof that the structure is unchanged; an identifier whose case alone changes, and output ClickHouse itself rejects (upper-cased case-sensitive names such as `MATCH`, `CUME_DIST`, `TUPLE(…)` / `VARIANT(…)` casts; `Int32 UNSIGNED`; `COLLATE` after `DESC`; `RENAME … ON CLUSTER c` rewriting the cluster as a table; a view's `COMMENT='x'`). These shapes are engine-local: rewriter-grpc keeps every clause, so they stay out of the shared corpus.

Known conservative refusals (valid ClickHouse the gate answers `UnsupportedStatement`; each fails closed and none is driver traffic):

- `SELECT TOP n WITH TIES` (Polyglot drops `WITH TIES`) and `BEGIN TRANSACTION` (regenerated as `BEGIN`).
- `INSERT … SELECT … FORMAT <name>` without `input()` followed by anything but comments; and, when the statement reads `input()`, any tail after the format name other than `[ \t]*\n?`, so a comment tail (`FORMAT TSV -- c`) and a `\r\n` tail are refused too.
- A digit-leading identifier made only of hex digits (`0-9`, `a-f`, `A-F`) and the characters `_ . x X p P` (`isNumberLike`), such as `1_e3`, `1__0` or `2024_dead`, which is spelled as a number and refused; and a number directly followed by a letter or `_` (`1a`). `2024_events` stays an identifier, because `v`, `t` and `s` are not among those characters.
- Streamed `input()` with parenthesised set-operation operands, which the parse gate already refuses.
- `SHOW CREATE role.t` / `policy.t` (and the other access-entity words) without `TABLE`; write `SHOW CREATE TABLE role.t` or quote the name.
- `MaterializeSQL` with `now()` combined with `startsWith`, `toStartOfDay`, `instr`, `CHAR_LENGTH` or `group_concat`: the materialize plugin falls open to the original SQL, and an SI agent INSERT with that combination is refused at ingress (nondeterminism) until the respelling follow-up lifts it.
- A column named `regexp`, `div` or `mod` next to one of those operators.

A raw access-entity statement (`CREATE ROLE` / `QUOTA` / `SETTINGS PROFILE` / `ROW POLICY`) with any quoted identifier, even an ordinary one such as `` `r1` ``, is refused in no-rewrite and static mode, because its text drops the quotes; dynamic requests refuse these statements anyway.

The column-modifier order check also refuses valid column declarations that Polyglot regenerates in an order ClickHouse rejects: `MATERIALIZED` / `ALIAS` / `EPHEMERAL` followed by `COMMENT`, `CODEC` or `PRIMARY KEY`, and `CODEC` or `TTL` followed by `PRIMARY KEY`. The native engine could not execute these before the check either (ClickHouse 26.2 rejected the regenerated SQL); the refusal only moves the failure from ClickHouse to the rewriter.

View column lists: a CREATE [MATERIALIZED] VIEW column's `DEFAULT` / `MATERIALIZED` / `ALIAS` / `EPHEMERAL` / `TTL` / `CODEC` / `COMMENT` is walked before the generator drops it, so a read in it is refused like the same CREATE TABLE column's; a read-free one that the generator drops is then refused by the mid-statement drop gate above. A view's `INDEX` over anything but a bare column is generated as the Rust debug form of its expression. With the storage-integrity surface active, a logical table named inside an opaque view INDEX / PROJECTION item gets the R2 `statement is not supported` refusal, not the SI IN-target message the same CREATE TABLE item gets, because the SI handlers see no structured node for it.

## ANTI-PATTERNS

- Do not import polyglot outside `internal/engine`.
- Do not let `internal/nameresolve` import `internal/engine`, handlers, or the polyglot SDK.
- Do not copy or regenerate protobuf definitions here; make contract changes in `github.com/housegate/rewriter-proto` and update the pinned module version.
- Do not treat `go test ./...` as proof of FFI-backed parity unless `POLYGLOT_SQL_FFI_PATH` is set.
- Do not make `RewriteErrorMessage` inversion failures break exception handling. `Service.RewriteErrorMessage` is best-effort and returns pass-through output with nil error on failure or empty input.
- Do not move statement dispatch out of `doRewrite` without checking reject normalization, `existence_clause`, and `statement_type` parity.
- Do not treat oracle divergences as harmless unless they are explicitly allow-listed in the relevant harness corpus/test.
- Do not mutate `third_party/polyglot-src` except through submodule bump workflows.
